# GitSync

GitSync 是一个基于 Tauri + React 的桌面应用，用于管理和同步多个本地 Git 仓库。

## 功能概览

- 仪表盘支持两种布局：`列表布局` / `卡片布局`，卡片布局使用保持排序阅读顺序的 row-major 网格。
- 仓库卡片支持单仓库操作：同步、暂停/恢复、查看错误、更多菜单。
- 当仓库目录被删除或移动时，卡片会进入“目录缺失”态：
  - 卡片显示半透明遮罩与错误说明，并禁用同步/更多操作，避免误触发无效任务
  - 支持在遮罩上直接“一键从列表移除”该仓库
  - 已标记为目录缺失的仓库会被自动跳过状态抓取、远端 `fetch` 和自动同步轮询
- 仓库卡片状态提示采用分层展示：
  - 右上角标签徽标：仓库当前主状态（已同步/有改动/待拉取/冲突/错误等）
  - 右上角附加标识：启用同步后脚本时显示“自动脚本”标识
  - 中部状态徽标：改动数、领先/落后计数
  - 下方提示条：需要优先处理的信息（本地改动、冲突、同步错误、远端新提交）
- 仪表盘仓库统一列表使用 `全部仓库 / 已同步 / 有新改动 / 本地有未提交改动 / 同步或本地有改动` 五种状态筛选，并支持全局名称、提交时间、同步时间排序：
  - `同步或本地有改动` 是并集语义：命中“远端有新改动”或“本地有未提交改动”任一条件即入选（两类都有也入选）；`有新改动` 与 `本地有未提交改动` 仍各自精确匹配单一条件。内部持久化 key 仍为 `new-and-local-changes`
  - 数据管线为“状态筛选 → 全局排序 → 仓库名搜索 → 列表/卡片布局投影”，搜索无结果保持独立文本提示
  - filter empty state 由当前筛选和搜索后的 projection 是否为空决定，不由全局仓库数量决定；初次加载完成前不显示空状态
  - 提交时间排序只比较当前分支最新 commit 的时间；同步时间排序只比较 GitSync 最近一次成功同步完成时间，两者不会互相替代
  - 同步时间兼容旧版秒级与当前毫秒级时间戳；失败/取消的同步历史不参与排序，从未同步的仓库在升序和降序中都排在最后
  - 当前排序为提交时间时，卡片时间行标明“提交时间”；当前排序为同步时间时，卡片时间行标明“上次同步”，让排序依据可直接观察
  - 列表布局按排序数组逐行渲染，卡片布局按从左到右、从上到下的 row-major 顺序分行，视觉阅读顺序与排序契约一致；历史保存值 `masonry` 仅作为卡片布局的兼容 key
  - 仓库状态仍只看当前分支与工作区；同步中/排队中、未提交改动、冲突、ahead、behind 等状态由卡片自身展示，不再通过 Dashboard 分组改变列表语义
  - `获取更新中...` 与 `刷新状态中...` 属于被动刷新，点击遮罩仍可发起该仓库的同步；`检查中...` 及分支操作期间保持不可点击
  - 过滤结果支持“同步当前筛选”，作用域包含当前状态筛选与搜索后的可见仓库，并跳过暂停仓库
- Dashboard filter empty state 使用 `src/dashboardEmptyStates.js` 的统一配置和 `src/assets/dashboard-empty-states/{light,dark}/*.webp` 十张透明 WebP；跟随系统主题时根据实际生效主题实时切换资源。
- 仪表盘右上角支持“搜索”按钮：
  - 点击后展开搜索框，按“仓库名”实时筛选当前状态筛选列表
  - 再次点击“搜索”或点击空白区域会自动收起并清空关键词
  - 搜索条右侧显示匹配数（如 `匹配 3/8`）
- 仓库卡片元信息（路径、提交、同步时间）统一使用自定义悬浮卡片样式：
  - 常态下单行省略，避免挤压卡片布局
  - 仅在文本被截断时显示悬浮卡片
  - 最新提交悬浮内容包含 hash、message、author、date
- 仓库卡片分支行支持“分支总览”悬浮窗：
  - Dashboard filter 仍只使用当前分支状态；获取远程更新后，仓库卡片会以非模态提示展示非当前分支落后或远端新分支，完整信息仍在悬浮窗中展示
  - 展示本地/远端分支数量与更新摘要（新分支、落后分支、有分叉、upstream gone、比对失败、其它 worktree 检出）
  - 口径说明：卡片“落后 N”是当前分支落后提交数；分支总览“落后分支 N”是悬浮窗内处于落后状态的分支数量
  - 分支列表支持内部滚动，避免分支较多时撑破卡片或遮挡其它仓库
  - 工作区干净（无未提交改动/冲突，且未同步中/排队中）时，非当前本地分支显示“切换”按钮，远端仅存在分支显示“切换并跟踪”按钮
  - 只有一个可安全处理的分支动态时，卡片提示提供快捷按钮：落后的本地分支可“切换并更新”，远端新分支可“切换并跟踪”；多个分支、分叉或异常状态只提供“查看详情”
  - “切换并更新”会重新 fetch，并只对没有本地领先提交的目标分支执行 fast-forward；不会触发完整同步中的 stash、push 或 merge commit
  - upstream gone 分支可在悬浮窗中显式“重新绑定”唯一同名远端，或“取消上游”；整行点击不再触发写操作
  - 切换/跟踪/重绑/取消上游完成后只刷新目标仓库的远端、当前状态和缓存元数据，不触发全量仓库刷新，也不更新 `last_sync_at`
  - 分支切换过程会在卡片动作区与分支悬浮窗内显示“切换中 / 更新中”阶段提示
- 侧边栏统计区展示当前全局同步模式（自动/手动）。
- 侧边栏悬停“全部同步”后会浮出“按改动同步”按钮：
  - 本地存在已提交但未推送的提交（ahead）时会自动 `push`
  - 远端存在未拉取的新提交（behind）时会自动 `pull`（优先使用当前分支跟踪的 `remote + merge` 作为显式目标）
  - 无 ahead/behind 提交差异时会跳过同步
- 同步历史中心：
  - 按仓库分组展示历史记录
  - 支持分组收起/展开（含过渡动画）
  - 分组收起/展开箭头在深浅色主题下提升可见性
  - 支持关键词检索、结果筛选、来源筛选
  - 支持总量/成功/失败/取消/平均耗时统计
  - 支持复制同步诊断日志，可按 `requestId`、`jobId`、仓库和阶段追踪一次请求从检查、排队到后端返回的过程
  - 诊断日志不记录仓库路径、提交信息、Git 命令、远端地址或原始错误文本
- 更多菜单支持：
  - 打开仓库目录
  - 打开 GitHub 仓库（自动识别 `origin` 远端地址）
  - 使用默认应用打开（例如 VSCode）
  - 使用终端应用打开（终端应用可在设置中自定义）
  - 同步后脚本开关（启用后每次仓库同步完成自动执行；脚本后台执行，不阻塞同步状态）
  - 选择脚本文件（仅支持仓库内脚本，且按系统限制：Windows 支持 `.sh/.command/.bat/.cmd/.ps1`，macOS/Linux 支持 `.sh/.command`）
  - 脚本执行日志窗口（实时滚动输出，支持查看最近执行会话）
  - 清空脚本选择（并自动关闭开关）
  - 根据可视区域自动选择向下/向上弹出（避免底部卡片被窗口截断）
  - 菜单开启动画按最终弹出方向渲染，避免底部卡片出现“先向下闪现再上移”的跳动
  - 移除仓库
- 批量操作模式（默认隐藏工具条）：
  - 批量同步
  - 批量暂停
  - 批量恢复
  - 批量移除（带二次确认）
- 仪表盘右上角支持“获取更新”按钮：手动触发全部未暂停仓库执行远端 `fetch`，完成后自动刷新卡片状态。
  - 手动获取失败时会弹出失败明细汇总，指出哪些仓库当前状态可能不是最新
  - 应用首次启动自动执行的初始化 `fetch` 若失败，会显示轻提示 toast，并把对应仓库标记为“待刷新”
- 导入入口升级为菜单交互：点击“导入仓库”后可选择
  - 本地导入：从本机选择一个或多个 Git 仓库目录（含去重）
  - 克隆仓库：输入远程地址与本地保存路径，克隆完成后自动加入仓库列表并应用默认同步设置
  - GitHub 仓库：在设置页登录 GitHub 后浏览账号仓库，支持搜索、分页加载、多选批量克隆，完成后自动加入仓库列表
  - 顶部“导入仓库”按钮弹出菜单与触发按钮右侧对齐，避免菜单视觉偏移
  - 底部导入卡片在收起/展开状态下都与仓库列表保持一致的左右边界
  - 底部导入卡片展开后左右区块固定 `1:1`，并与仓库卡片列分割保持视觉对齐
  - 克隆入口图标更新为分支链路样式，和仓库相关语义更一致
- GitHub 账号集成：
  - 使用 GitHub Device Flow 登录/登出，access token 存入系统凭据管理器（macOS Keychain / Windows Credential Manager）
  - 应用启动时不主动读取系统钥匙串；只有点击 GitHub 登录或 GitHub 仓库入口时才按需恢复登录态，减少开发/临时构建反复触发 Keychain 授权弹窗
  - 设置页的 GitHub 区块统一提供登录、账号状态、登出和默认隐藏开关，登录成功后自动打开仓库浏览器
  - GitHub 仓库浏览器支持按仓库名、描述、语言搜索，按可视性/语言筛选，并可按创建时间或更新时间排序
  - 仓库行显示公开/私有、语言、star、默认分支、更新时间、创建时间，并提供“打开”按钮直接访问远程仓库页面
  - 设置页可开启“默认隐藏已添加仓库”，打开浏览器时默认隐藏已在仓库列表中的 GitHub 仓库
  - 浏览器内仍可临时切换“隐藏已添加”，已在列表中的仓库会禁用选择，避免重复克隆
  - 批量克隆在浏览器内弹出二级对话框，支持选择本地目录、并发克隆、单个任务取消、取消全部和完成汇总
  - 仓库列表刷新时会同步当前 Git branch 与 preferred remote，避免 GitSync 缓存的旧 remote 影响 GitHub 已添加仓库判断
- 导入仓库支持单选/多选，并包含去重：
  - 本次选择内去重
  - 与已添加仓库去重
  - 自定义导入结果弹窗（成功/跳过/失败明细）
- 自定义对话框体系：冲突处理、错误日志、删除确认、通用提示。
- 主题支持：`浅色` / `深色` / `跟随系统`。
- 自动同步支持 5 秒到 24 小时区间，支持秒/分钟/小时单位切换（内部仍以秒存储）。
- 设置页“Git 任务并发数”（`maxSyncConcurrency`）统一控制 Git 相关任务并发：同步队列、仓库状态读取、定时远端 Fetch、同步前检查。
- 设置页支持“定时远端 Fetch 间隔”：对未启用自动同步的仓库按该间隔执行远端 `git fetch`，仅刷新远端状态，不自动拉取。
- 设置页可配置默认打开应用，并作为卡片“用 XXX 打开”的来源。
- 设置页可配置默认终端应用，并作为卡片“用终端打开”的来源。
- 设置页支持“自动脚本日志弹窗”开关：控制同步后自动触发脚本时是否自动弹出日志窗口。
- 设置页支持“只在拉取后执行脚本”开关：开启后仅在本次 `pull` 真实同步到远端新提交时执行脚本（`Already up to date` 不触发）；关闭后本次“有效 pull”或 `push` 任一动作都会执行。
- 设置页 GitHub 区块支持登录、登出和“默认隐藏已添加仓库”开关：控制 GitHub 仓库浏览器每次打开时是否默认过滤已在列表中的仓库；过滤前会使用当前 Git remote 刷新本地仓库元数据。
- 跨平台协作默认启用 LF 行尾规范（`.gitattributes` + `.editorconfig`），降低 Win/mac 来回切换时的“无内容改动但 Git 显示已修改”问题。
- 稳定性优化（2026-03-02）：
  - 窗口失焦时暂停仓库状态轮询与自动同步定时器，回焦后自动补刷新。

  - 设置页默认同步配置改为后端批量更新（单次落盘），避免前端无上限并发写入。

  - 后端新增“同仓库 Git 命令互斥锁”，对 `sync_repo` / `get_repo_status` / `refresh_repo_remote` / `check_sync_prerequisites` 串行化执行，降低 `index.lock` 冲突概率。
- 稳定性优化（2026-04-03）：
  - `get_repo_status` / `check_sync_prerequisites` / `sync_repo` 在执行 Git 命令前会先校验仓库路径，目录缺失时直接返回明确错误。
  - 前端会把目录缺失仓库标记为“跳过态”，避免反复触发无效的远端刷新与同步任务。
  - 删除仓库改为“前端乐观移除 + 后端批量删除 + 按需回滚”，目录缺失卡片上的“从列表移除”与普通移除都可秒响应。
  - 后端新增 `remove_repos_batch`，一次落盘完成批量删除，并返回 `requested_count/removed_ids/missing_ids` 供前端精确校准结果。
  - 删除期间自动 full 刷新会降级/跳过，避免删除确认后被重型状态抓取打断体感。
- 稳定性优化（2026-04-06）：

  - 仓库卡片会展示“待刷新”提示与失败相对时间（如“2 分钟前”），便于判断状态陈旧程度。
  - 手动“获取更新”失败会弹出失败汇总；首次启动自动 `fetch` 失败改为轻提示 toast，减少打断。
- 稳定性优化（2026-06-05）：
  - 应用从后台回到前台时先执行轻量仓库列表刷新，并跳过紧随其后的自动 full 刷新，减少 dashboard 短暂空白或全量重绘感。

  - 通过约束右侧控件收缩与单位文本换行策略，保证 Win/mac 显示一致。

## 环境要求

- Node.js `^20.19.0` 或 `>=22.12.0`
- npm 9+
- Rust（建议通过 `rustup` 安装）
- 系统已安装 `git`

可先检查：

```bash
node -v
npm -v
rustc -V
git --version
```

## 快速启动（桌面应用）

在项目根目录执行：

```bash
npm ci
npm run tauri:dev
```

`npm run tauri:dev` 会同时启动前端开发服务和 Tauri 桌面壳。

### GitHub 登录配置

GitHub Device Flow 需要 OAuth App 的 `client_id`。开发或打包前任选一种方式配置：

- 运行时环境变量：`GITSYNC_GITHUB_CLIENT_ID=xxx`
- 开发模式项目根目录文件：`github_client_id`
- 生产环境用户配置：`~/.gitsync/github_client_id`
- 编译时嵌入：`GITSYNC_GITHUB_CLIENT_ID=xxx cargo build`

GitHub access token 仅写入系统凭据管理器，不写入 `repos.json`。

## 仅启动前端（不启动桌面壳）

```bash
npm run dev
```

## 构建

前端构建：

```bash
npm run build
```

前端并发逻辑测试：

```bash
npm test
```

桌面应用构建：

```bash
npm run tauri build
```

使用仓库脚本构建（可选）：

```bash
# macOS/Linux
./build-app.sh

# macOS: 跳过 DMG 临时 Finder 排版窗口（构建更安静）
./build-app.sh --skip-dmg-ui

# Windows
build-app.bat
```

说明：

- `build-app.command` 双击后会直接交给 `build-app.sh` 执行；在 macOS 的 Terminal/iTerm 中，构建成功时会静默关闭当前窗口，不再弹出“是否终止正在运行的进程”的确认框，构建失败时会保留窗口方便查看日志。
- 在已有 shell 中手动运行 `./build-app.sh` 时，macOS 的 Terminal/iTerm 也会在成功后自动退出；如需保留窗口查看日志，可使用 `BUILD_APP_AUTO_CLOSE=0 ./build-app.sh`。
- `build-app.bat` 在 Windows 的 `cmd` 中成功构建后也会自动退出当前命令窗口；如需保留窗口查看日志，可使用 `set BUILD_APP_AUTO_CLOSE=0 && build-app.bat`。若从其他终端（如 PowerShell）调用，则会结束脚本对应的 `cmd` 进程并返回外层终端。

## Tag 自动发布版本（GitHub Release）

仓库已内置工作流文件：`.github/workflows/release-on-tag.yml`。

触发规则：

- 当你 push `v*` 格式的 tag（例如 `v1.2.1`）时，自动执行发布流程。

发布流程会自动做以下事情：

1. 校验 `src-tauri/tauri.conf.json`、`package.json`、`src-tauri/Cargo.toml` 的 `version` 是否一致。
2. 校验 tag 是否等于 `v<version>`（例如版本是 `1.2.1`，tag 必须是 `v1.2.1`）。
3. 在 `macOS + Windows` 构建 release 包。
4. 自动创建 GitHub Release，上传 macOS DMG 与应用内更新包，以及 Windows 便携版 `GitSync.exe`、NSIS 安装包和更新签名。

macOS 发布说明：

- CI 使用 Apple Silicon runner 构建 DMG。
- 若未配置 Apple 签名/公证 secrets，下载后的 DMG 在部分 macOS 上可能被 Gatekeeper 提示“已损坏”；这通常和签名/公证及下载隔离有关，不是你本机架构问题，本地构建常因未经过互联网下载隔离而不触发该提示。
- `APPLE_CERTIFICATE`、`APPLE_ID` 等 secrets 需要 Apple Developer 账号（用于签名与公证）。没有开发者账号时可继续构建/分发，但无法做到所有用户“下载后双击即开”。

无 Apple Developer 账号时的 macOS 分发建议：

1. 正常发布 DMG（本项目 CI 可正常产出）。
2. 在 Release 说明中明确提示：首次安装可能需要手动放行。
3. 用户将 App 拖入 `/Applications` 后，执行：

```bash
xattr -dr com.apple.quarantine "/Applications/GitSync.app"
```

4. 然后在 Finder 中对应用右键 -> 打开（首次一次即可）。
5. 这是临时可用方案；若要实现“下载后直接双击打开”，仍需 Apple Developer 签名+公证。

macOS 与 Windows 应用内更新：

- 应用启动后自动检查一次公开 GitHub Release；发现新版后先在后台下载，下载完成后才提示安装。设置页也可手动检查。更新检查与下载不要求登录 GitHub。
- 更新清单位于 `https://github.com/Zephinel/GitSync/releases/latest/download/latest.json`。发布工作流在同一个 Release 中上传清单、两平台安装包和对应签名；客户端用配置中的公钥验证更新。
- Windows NSIS 安装版与 macOS `.app` 支持应用内更新；Windows 便携版 `GitSync.exe` 需手动替换。应用正在执行 Git 操作时会阻止安装，可在操作结束后重试。
- 首次公开版为 `0.1.0`。旧私有版安装需要手动安装一次公开版。
- 发布前须将新公开版更新私钥安全地配置为仓库 Actions secret `TAURI_SIGNING_PRIVATE_KEY`；它对应 `src-tauri/tauri.conf.json` 中的公钥，不得提交进 Git。若私钥设置了密码，还需配置 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。
- 没有 Apple Developer 签名与公证时，macOS 首次 DMG 安装仍可能需要手动放行。Tauri 更新签名与 Apple 签名是两套独立机制。
- GitHub 的 `/releases/latest` 会选择非 prerelease 的发布版本；当前工作流使用单一更新通道，发布前需确认这符合预期。

首次真实应用内升级验证需在后续 `0.1.0 → 0.1.1` 发布时，分别用 macOS App 和 Windows NSIS 安装版检查下载、安装、重启及本地数据保留。静态测试和构建不能替代这一步。

版本迭代建议：

- 按语义化版本递增发布，例如补丁版 `2.1.3 -> 2.1.4`、次版本 `2.1.x -> 2.2.0`。
- 每次发布前，把 `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` 都改成同一个新版本号。
- 然后打对应 tag 并推送，tag 必须等于 `v<version>`。

示例命令（发布 `<x.y.z>`）：

```bash
git add package.json package-lock.json src-tauri/tauri.conf.json src-tauri/Cargo.toml src-tauri/Cargo.lock
git commit -m "chore(release): bump version to <x.y.z>"
git push origin main

git tag v<x.y.z>
git push origin v<x.y.z>
```

## 常用操作说明

1. 导入仓库：在仪表盘点击“导入仓库（可多选）”，可选择本地导入、手动克隆或 GitHub 仓库浏览。
2. 切换布局：仪表盘右上角图标切换列表布局/卡片布局。
3. 进入批量模式：点击“批量操作”，选择仓库后执行批量动作。
4. 手动刷新远端：仪表盘右上角点击“获取更新”，会对全部未暂停仓库执行远端 `fetch`；若后台刷新进行中，会自动串行排队，但顶部加载态只等待覆盖本次手动请求的那一轮完成并回填到卡片状态。
5. 配置同步模式与定时远端 Fetch：设置页中可切换自动/手动模式，并单独调整手动模式仓库的定时远端 Fetch 间隔。
6. 配置默认应用：设置页中“默认打开应用”，选择后卡片显示“用 XXX 打开”。
7. GitHub 仓库批量克隆：先在设置页登录 GitHub，登录成功后会自动打开仓库浏览器；已登录时也可从导入菜单或底部导入卡片进入“GitHub 仓库”，搜索/筛选/排序并多选仓库后选择本地保存目录。克隆任务会并发执行，可单独取消，也可取消全部。
8. 隐藏已添加仓库：在设置页 GitHub 区块开启“默认隐藏已添加仓库”，之后打开 GitHub 仓库浏览器会默认过滤已在列表中的仓库。
9. 查看错误：卡片“错误”按钮仅在存在错误日志时可点击。
10. 配置同步后脚本：卡片“更多”中开启“同步后执行脚本”，首次开启会要求选择脚本；后续开关不再重复选择，可手动“清空脚本选择”后重选。脚本失败会单独提示，但不会把本次 Git 同步改为失败。
11. 脚本执行兼容性：GitSync 执行脚本时会尽量贴近终端运行环境（macOS 使用伪终端 + `bash -l`）；Windows 会将 `canonicalize()` 产生的 `\\?\` 路径转为常规路径后再交给 `cmd`。
12. “执行脚本”和“同步后自动触发”都会调用系统终端执行，行为与双击脚本一致；macOS 会优先复用 Terminal 当前前台窗口以避免额外空白窗口，Windows 通过 `start /D <repo>` 在仓库目录启动终端，日志窗口用于展示触发记录与执行命令。
13. 若开启“只在拉取后执行脚本”，自动脚本只会在本次 `pull` 真实同步到远端新提交后触发；若关闭，则本次“有效 pull”或 `push` 任一动作都会触发。
14. 卡片分支行悬停可查看“分支总览”；当仓库无未提交改动且无冲突时，可直接点击目标分支切换。

## 常见问题

- 报错找不到 `tauri` 命令：先执行 `npm install`，确保本地安装了 `@tauri-apps/cli`。
- 报错 Rust 相关工具缺失：安装 Rust 并重开终端后再试。
- 同步异常排查：先在同步历史中心复制诊断日志，再按需查看应用数据目录下的日志文件（如 `panic.log`、`sync-debug.log`）。`git reflog` 只能证明仓库发生过更新，不能单独证明 GitSync 的同步链路已经完成。

## 分支状态刷新说明（2026-03-15）
- 仪表盘页面处于前台可见时，仓库状态每 10 秒轮询一次，分支名会随状态同步刷新。
- 应用窗口从失焦恢复到聚焦，或页面从隐藏恢复可见时，会立即补一次本地状态刷新（卡片可能短暂显示“刷新状态中...”）。
- 应用启动后会自动执行一次远端 `fetch`（全量未暂停仓库），用于初始化远端状态。
- 远端 `fetch` 的后续触发由“定时远端 Fetch 间隔”配置或手动点击“获取更新”完成，不再由仪表盘前台轮询额外触发。
- 非仪表盘页面仅刷新仓库列表，不执行全量 `get_repo_status`，用于降低后台开销。
- 从分支总览切换、跟踪远端、重新绑定 upstream 或取消 upstream 时，会对目标仓库追加一次定向远端刷新，再重载分支总览与卡片状态；这段过程会明确显示“切换中...”与“已切换，正在更新状态...”，且不会更新 `last_sync_at`。

## 同步 Push 与 Tag 规则（2026-03-16）
- 仓库同步流程中的推送命令使用 git push --follow-tags。
- --follow-tags 只会自动推送“可跟随标签”：
  - 仅注释标签（annotated tag），不包含 lightweight tag。
  - 标签指向的提交需要在本次推送分支历史内可达。
  - 远端不存在同名标签时才会一并推送。
- 若需要“无条件推送所有本地标签”，请使用 git push --tags（当前应用默认不采用该策略）。
